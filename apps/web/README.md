# TradeLab web client

SvelteKit 3 + Svelte 5 (runes), TypeScript strict, static build (`adapter-static`) with an offline service worker. The C++ engine runs as WebAssembly inside a Web Worker; the UI only ever receives the state up to the current step.

Behavior contract: `openspec/changes/add-web-client/` (web-client + terminal-ui specs). Deviations of the current slice are listed in its `design.md`.

## Run

Requires Node 22 and Emscripten (`brew install emscripten`, or emsdk with `emcmake` on `PATH`) for the engine build.

```bash
npm install
npm run engine:build   # compiles engine/ to WASM -> src/lib/engine/wasm/tradelab.mjs (gitignored)
npm run engine:size    # fails when that module is 400 KB gzipped or more (CI runs it)
npm run engine:types   # regenerates src/lib/engine/types.ts from engine/idl/tradelab.idl
npm run dev            # http://localhost:5173 ; append ?seed=123 for a reproducible market
npm run build && npm run preview   # production build incl. service worker (offline mode)
```

Rebuild the engine (`npm run engine:build`) after any change under `engine/`, and regenerate the types (`npm run engine:types`) after any change to `engine/idl/tradelab.idl`; CI fails on stale generated types.

## Test

```bash
npm run check      # svelte-check (app + service worker)
npm test           # Vitest unit tests (src/lib/game/*.test.ts)
npm run test:e2e   # Playwright: builds, serves on :4173 (override with E2E_PORT), runs e2e/ in Chromium and WebKit
npm run budget:size  # after a build: initial JS + WASM must stay under 1 MB gzipped
E2E_API_PORT=8787 npx playwright test   # the pack catalog served by services/api (see "Catalog from the API")
```

`PLAYWRIGHT_CHROMIUM_PATH=/path/to/chromium` reuses a local Chromium instead of `npx playwright install chromium` (WebKit: `npx playwright install webkit`). Playwright projects: `chromium` runs every spec except the deploy, budget and API catalog specs; `webkit` runs `a11y`, `browser-support` and `storage` (Playwright's WebKit cannot emulate offline through a service worker); `deploy` runs `deploy.spec.ts` alone after both, because its simulated deploy (`scripts/previewDeploy.ts`, a `vite preview`-only plugin behind `/__e2e-deploy/<id>`) changes the service-worker script for every browser. `--project=chromium` runs one project. `budgets` runs `e2e/budgets.spec.ts` last and alone, so other workers don't compete for the CPU it measures. It holds the performance budgets (mission ready < 3 s, p95 advance latency < 100 ms, a 5,000-bar pack ready < 3 s and zooming at 60 fps); `CPU_THROTTLE=3` runs it on a slowed-down CPU to check the headroom. CI (`.github/workflows/web.yml`) runs engine build, check, unit, build, the size budget, E2E and the API catalog E2E.

Game rules, fills, scoring and the debrief come from the engine; the seeded reveal of a built-in mission (regime spans, event outcomes) comes from `tl_mission_reveal` through the worker's `reveal` request, which the worker refuses while the run is active (`src/lib/engine/reveal.ts`, checked by `reveal.test.ts`), and the debrief draws it as a regime band, a signals-by-regime table (`RegimeReveal`) and a per-release table (`ReleaseReveal`: consensus, drawn outcome and size, gap, reaction, positioned before or after, implied against realized move); the client formats engine decimal strings for display and never computes authoritative state (ticket previews in `sizing.ts`/`optionsMath.ts` mirror engine formulas for display only). Runs persist as an append-only action log in IndexedDB (`tradelab` DB v3: `runs`, `actions`, `meta`, `packs`, `checkpoints`); every 20 actions the engine's checkpoint (its `RunState`, no scenario bars) is stored as the run's latest, with the option series seen so far (kind, strike and expiry, named in the shown locale; an expired series is no longer in the restored state), and resume restores it and replays only the actions after it (or the whole log when the checkpoint was written by another engine build, whose checkpoint format may differ, or is refused). A run record also keeps its start options (advice allowance, intel perks; campaign capital and leverage cap), its campaign link and its last equity, and `meta.progress` (version 2, `migrateProgress` reads older shapes) keeps the tutorials seen, the intel perks already explained, the advisor point balance (`points.ts`: start 3, cap 10, settled once per run id; a resumable run is settled, earning nothing, when another run is started), the campaign run, ended campaign runs and the missions assessed in a campaign (`campaign.ts`, `curriculum.ts`; a campaign mission is settled once per run id from the engine's final equity, and a left one from its last equity; a leg that reached its debrief also stores the engine's trade and cost facts, which `campaignReport.ts` adds up for the capstone's `CampaignReport`).

## Mission rules, lesson questions and assisted practice

The briefing renders the engine's `missionRules` (task 4.1): objectives (`objectives.ts`, PT-BR and en text per engine code, numbers in the locale), permissions and limits; the rail's liquidation warning uses the mission's distance, and the ticket (new order or protective stop) needs a ticked confirmation for a stop beyond liquidation when the mission asks for it; dragging a working stop on the chart to or past the liquidation price asks the same in a dialog (`ConfirmDialog`, `stopMovedBeyondLiquidation` in `chartDrag.ts`) before the move is sent. Briefing margin tiers never list a leverage above the mission's cap (`briefTiers`), and the `liq_buffer` finding names the mission's warning distance. `LessonQuiz` shows the mission's lesson questions (`tl_lesson` through the worker's `lesson` request; texts in `lessons.ts`, checked against `engine/rubrics/lessons.json` by `lessons.test.ts`); each answer is a logged `lesson` action (an engine command), so perk toggles on the briefing replay it onto the restarted run. The debrief adds `LessonResults` (answers and key) and `DecisionStrip` (the engine's act/hold/wait records). `AssistPanel` (terminal and debrief) rewinds to a chosen bar (`rewindPrefix` in `assisted.ts` rebuilds the run from its own actions) or starts the mission on another seed (the "back to bar" field is kept inside the rewind range, `clampRewindTurn`, so it always shows the bar the rewind goes to); lesson answers given on the briefing are kept by every rewind, even one to the first decision; the new run record carries `assisted`, starts without the advisor (the terminal hides the advisor panel, as for practice packs), and is skipped by `finishedMissions`, points and campaign settlement. E2E: `e2e/scoring-v11.spec.ts`.

## Ticket, rejections, accessible chart and shortcuts

- **Sizing:** the ticket sizes by quantity, notional (cr), % of equity (exposure: the notional is that share of equity) or risk % to a stop (`sizedQty` in `sizing.ts`, rounded down to the lot); every amount accepts the decimal comma, credit amounts (notional, margin) also the locale's thousands separator ("1.000" in PT-BR is one thousand, `parseAmount`), and the estimates show the resulting notional. While a liquidity shock the player can see covers the next bar (the engine's `liquidity` state field), the estimates use its wider spread and slippage (`costsOf`) and the ticket says so (`ticket-shock`); the briefing warns when the market has liquidity shocks (`contract.liquidityShocks`). The option ticket checks premium + fee (`optionBuyCost`, the engine's `feeRate`) against the available balance and shows the fee. The advisor's apply writes its stop and size the way the player would type them (`priceInputText`, `qtyInputText`: "41,8" in PT-BR).
- **Rejections:** a refused command shows the plain-language reason with the numbers behind it in the locale (`rejections.ts`): required vs available margin (orders, a lower leverage that re-margins the open position, adding margin), the margin left vs the initial margin, the leverage vs the cap. The engine returns only the code; the figures are the client's display estimates, quoted only when they explain the refusal (an option premium that fits while the engine also reserves the fee shows the plain reason, never "needed less than available").
- **States:** "no data" on the chart before any closed bar; "download interrupted" when a `.tlpack` cannot be read or is cut short (`packLooksCut` in `packs.ts`). Session expired, sync pending and device conflict wait for the backend.
- **Accessible chart:** `ChartTable` holds every closed bar in pages of 50 (the default page ends with the current bar, UX01) plus a text summary; it is visually hidden until "Table" opens it (Esc closes) or keyboard focus enters it. The canvas box is a keyboard slider: arrows, Page Up/Down and Home/End move the focused candle, its OHLCV and patterns are announced (`aria-valuetext`; a continuity bar, a data gap without trading, is tagged in the announcement and in its table row), Enter opens its pattern card, and Space still advances.
- **Shortcuts:** defaults in `shortcuts.ts` (Space, Shift+Space, B, S, X, P, A, M, O option chain, J run journal, ?), remappable in the menu settings and from the help overlay (`ShortcutSettings`), saved per viewer in localStorage (`tradelab.keymap.v1`). A key used by another action is refused naming it; Enter, Esc, Tab, arrows and Home/End/Page keys are reserved, with or without Shift. The help overlay and button hints show the current keys.

## Campaign, curriculum map and journal

The menu offers the campaign (missions in `campaignMissions()` order, capital carried through the engine's `startingBalance` start option, bankruptcy or less than `CAMPAIGN_MIN_CAPITAL` left ends the campaign run; ending it by choice asks first and leaves its mission in progress), free play (any mission, its own rules), the curriculum map (`CurriculumMap.svelte`: stage statuses from `curriculum.ts`, progress summary) and the journal (`Journal.svelte`: every run's plan entries from the `runs` store, newest first, filterable by mission; a run replaced by another before its end is stored as `left`). The curriculum's unlock rules are data in `curriculum.ts`; in a campaign mission a locked "leverage above 2×" becomes the engine's `leverageCap` start option, and the briefing lists what stays locked and which stage unlocks it.

## Intel perks

`perks.ts` holds the rules: Economic calendar at 1, Fast wire I at 2 and Fast wire II at 4 distinct built-in missions finished (`GameSession.finishedCount`, from the runs played to the end; imported packs do not count). A free-play run starts with every unlocked perk on; `PerkPanel` on the briefing toggles them (`GameSession.setPerk` restarts the not-yet-played run on the same seed with the new `newsLead`/`calendar` start options and updates its record), shows each locked perk's requirement, and explains a newly unlocked perk once (`progress.perksIntroduced`, written when the terminal opens). Campaign missions and pack runs start without perks. `NewsPanel` shows the announced calendar (`upcoming`: kind, bar and consensus, for every player), early headlines (EARLY, "public in N bars") and the calendar perk; auto-advance pauses when a headline arrives early (`newsArrived`). The debrief and the journal label runs whose start options used a perk "with intel" (`perksUsed`, `withIntel`).

## Imported markets (CSV and packs)

"Import CSV" in the menu opens a wizard: pick a file, confirm what the engine cannot know (asset, pair, venue, bar interval, timestamp unit, volume unit, leverage cap; the unit and interval are guessed from the first rows), validate, then create a practice mission. The engine (`tl_csv_validate`, `tl_pack_build_csv`) does all the checking, so the errors are the same on every client; the wizard only translates their codes (`csvIssueText`, `csvMetaText` for refused declared values, `packReasonText` for build refusals). The worker hands the CSV text to the engine through the WASM heap (`withText` in `engine.worker.ts`), not as a `ccall` string, which Emscripten copies onto its 64 KB stack; any string argument that can grow past a few KB must do the same. If an engine call traps, the worker drops the module and loads a fresh one on the next request. The result is a private `.tlpack`, masked to a price base of 100 and signed by this device's key, whose seed is created once and kept in the `meta` store. Packs are verified by the engine before they are installed by digest (file in OPFS, index in the `packs` store; see below) and again when a run starts or resumes. A run on a pack records `packDigest`, and resuming replays its log on that pack. "Load pack" installs a `.tlpack` file only if it is signed by this device or by a key pinned in `PINNED_PUBLISHER_KEYS` (`src/lib/game/packs.ts`; today the development catalog key). Mid-run, the UI shows these markets as KNOWN (a synthetic pack as SYNTHETIC, in the menu row, the catalog and the top bar: `marketTagKey`; the pack's mode is kept in the packs store) and never shows the real asset or prices; the debrief shows the reveal from the engine (the CSV-import source and transformation note are translated by `revealTexts` in `src/lib/game/debrief.ts`). A synthetic pack (`marketMode` `synthetic`, e.g. from `packer generate`) has no real market behind it: the briefing calls it a synthetic pack (titled after the mission it was generated from, e.g. "Treino · Véspera (pacote sintético)", or a generic synthetic-pack text, never its raw scenario id) and the debrief says it was generated, with no transformation note. The journal and the menu's resume line name a pack run by its origin (catalog or imported), like the briefing. "Play again" after a pack run starts the same pack on a new seed (`GameSession.playAgain`). Practice runs start without the advisor and never change the advisor point balance. When the report lists gaps, the wizard offers to join the bars (default) or fill each gap with bars without trading (engine policy v17, metadata `gapFill`: indicators skip them or carry the last close forward); the chart draws them as shaded slots with a dashed line at the carried close, the readout and the accessible table say "no trading", and a legend counts them with the gap policy in its tooltip. The briefing states whether positions are marked at the last price (`contract.markFromLastPrice`); with a mark series (pack schema 2) the account `mark` serves margin, liquidation and funding only, and the ticket, chart drags, calibration question and option ticket use the last close (`lastPrice.ts`, `e2e/pack-v2.spec.ts` on `e2e/fixtures/mark-v2.tlpack`), and the option ticket refuses a series inside its settlement window (`settling`, reason `series_settling`).

## Academy lessons

Stages without a mission are taught by short lessons (`academy.ts`; today Foundations: "Reading a bar"). Each lesson runs concept, demonstration, decisions and a transfer exercise on another market and window; a wrong answer explains and lets the player choose again, and the end screen shows the answers right on the first try. Charts (`LessonChart.svelte`) are labeled illustrative, scale from the closed bars only and hatch the unknown future; a screen-reader table lists the bars. The curriculum map starts and repeats lessons; completion is stored in `progress.lessonsDone` and passes the lesson's stage. Academy lessons are client data, unlike a mission's lesson questions (`lessons.ts`, scored by the engine). Lessons never gate the campaign, so a lesson-only stage never blocks the stages after it.

## Pack catalog and downloads

"Pack catalog" in the menu reads a manifest from `VITE_CATALOG_URL` (build time; default the static `/catalog/catalog.json`). Downloads (`download.ts`) fetch 64 KB byte ranges and commit each chunk to IndexedDB before the next request, so an interrupted, paused or reloaded download resumes where it stopped ("Resume download"); a server that ignores Range is accepted. The complete file must match the manifest's size and SHA-256, then the engine verifies its signature against `PINNED_PUBLISHER_KEYS` and it is installed into the pack store (OPFS, see below; verify-then-install); installed packs play from the catalog or the practice list. A pack keeps where it came from (`origin` in the packs store: `catalog`, or imported on this device), so the briefing and the debrief reveal call a downloaded pack a catalog pack, not "a market you imported"; "Play again" on a practice debrief starts the same pack on a new seed. In an installed app with a service worker, a fresh download uses Background Fetch and the page installs it when it finishes. The quota is shown and a download that does not fit does not start; the service worker keeps the Background Fetch cache (`tradelab-downloads-v1`) across updates until the page installs the pack. Offline, the last catalog seen is listed with downloads disabled; a server error shows "unavailable" with a retry. `/catalog/*` and `/audio/*` are never precached (`isCatalog`, `isAudio` match both URL pathnames and the build manifest's slash-less asset paths); the catalog is never cached and audio is cached on first play. A catalog entry may name its pack's market mode (`mode`, optional) for its tag.

**Catalog from the API.** `services/api` serves the same manifest at `GET /api/v1/scenarios` (entries' `file` is `packs/<digest>`, which resolves to `GET /api/v1/packs/<digest>`: 206 byte ranges, strong `ETag`, entitled packs only with a token holding the entitlement). To use it, build with `VITE_CATALOG_URL=/api/v1/scenarios` and serve `/api/*` from the API on the page's origin: in production the reverse proxy in front of the web host (design D4a; the API sends no CORS headers), locally `TRADELAB_API_PROXY=http://127.0.0.1:8000` makes `vite dev` and `vite preview` forward `/api/*` (run the API with `TRADELAB_PACKS_DIR=<repo>/apps/web/static/catalog` to serve the sample packs). The web client sends no token yet (sign-in is task 6.2), so it lists and downloads free packs only. `E2E_API_PORT=8787 npx playwright test` runs `e2e/catalog-api.spec.ts` against a real API: it starts `services/api` on that port (needs `uv` and the native engine library, `cmake --build engine/build/native-release --target tradelab_capi`), builds the app with the API catalog URL, proxies `/api` from `vite preview` and downloads a pack with an interrupted, resumed Range download. It rebuilds `build/`, so do not run it at the same time as the regular suite in the same checkout.

The sample packs are synthetic markets (seeded random walks) built through the packer by `scripts/build-sample-catalog.py --seed-file <seed>` (needs the native engine library and the bindings/python dev group): the engine masks each window into a pack source, the manifest records the market as synthetic with its license, the data files are zstd-compressed and the pack is signed under the development catalog key (`DEV_CATALOG_KEY` in `packs.ts`, a `publisher-` id) and checked for publishing. The seed is kept outside the repository; rebuilding with another seed needs the new public key pinned. Being synthetic, a sample pack is briefed as a synthetic catalog pack and revealed as generated in the debrief. `--only <slug>` rebuilds one sample and keeps the others' files and digests. Market C (`sample-c-shock`) is a pack schema 2 sample: its story (encoded like the packer's `events.json`) has two liquidity-outflow headlines, each followed by a liquidity shock, and it carries its own mission texts and objectives, so it is briefed with its own title and briefing and the briefing and ticket shock warnings appear in play (`e2e/catalog.spec.ts`).

A schema-2 pack's own mission texts (`texts` in the engine's pack summary) are kept with the installed pack (`StoredPack.texts`) and replace the generic pack title and briefing in the briefing, the top bar, the debrief, the menu's resume line and the journal (`withPackTexts` in `missions.ts`); its objectives come from the engine's `missionRules` like a mission's.

## Offline storage, updates and supported browsers

- **Packs** are installed by digest: the bytes go to the Origin Private File System (`packs/<digest>.tlpack`), the index to the IndexedDB `packs` store (bytes stay in the index where OPFS cannot write files). The practice section shows the space used and available (`storage.estimate()`); an install that does not fit is refused with the space missing. On every start each index entry is checked against its file: a missing or truncated file (evicted by the browser) is shown as "not on this device" with how to get it back, and neither a new run nor a resume starts from it (`packStore.ts`).
- **Engine pinning:** the engine is a content-hashed module (`_app/immutable/assets/tradelab.<hash>.mjs`). A run records the build it started on and the page copies that module into the `tradelab-engines-v1` cache, which the service worker keeps when a new version activates. After an update an unfinished run resumes on its own build, also offline, and the next run starts on the new one; builds no unfinished run needs are deleted when the menu refreshes (`engineCache.ts`). A run whose build is gone resumes on the current engine with a notice. The worker drives only builds whose C ABI (`tl_abi_version`) is the one it speaks (`ENGINE_ABI` in `src/lib/engine/abi.ts`; a build older than `tl_abi_version` counts as ABI 0): a pinned build with another ABI is not loaded, the run is not resumed and the menu says why (`engine.abiMismatch`); the run is stored as left (as starting another run would leave it), so the menu does not offer it again, and the next run starts on this version's engine (`e2e/updates.spec.ts`, with fake old builds).
- **Updates** install in the background and are offered only in the menu ("Nova versão disponível"), never mid-mission.
- **Unsupported browsers:** without WebAssembly or Ed25519 in WebCrypto the page shows which feature is missing instead of the game (`browserSupport.ts`).
