# Design: add-deterministic-engine

## Context

Four clients (web, desktop, iPad, Android later) and one server must agree bit-for-bit on every fill, margin figure, funding payment, liquidation and option premium. The desktop client is C++20, so a C++20 core removes a language from the stack (v0.1 proposed Rust). Option pricing needs transcendental functions, which are not bit-identical across `libm` implementations (glibc, Apple libm, musl/Emscripten), so determinism must be designed, not assumed.

## Goals / Non-Goals

**Goals:** one engine, identical results on native/WASM/Python/Swift; explainable accounting; cheap to test with golden vectors; small, embeddable, no dependencies at runtime.

**Non-Goals:** realism beyond what teaching needs (no order book, no market impact); performance beyond ~1 ms per step on mid-range phones.

## Decisions

### D1. C++20, header-light static library, C ABI facade
- `engine/include/tradelab/*.hpp` (C++ API) plus `engine/include/tradelab/c_api.h` (stable C ABI: opaque `tl_run` handle; commands take scalars and decimal strings, results and state are returned as UTF-8 JSON with monetary values as decimal strings). A run is created from a built-in mission id and a seed (`tl_run_create`); the scenario is generated inside the engine. JSON was chosen over a binary encoding to keep the bindings trivial; state never round-trips through it (only checkpoints, which are hex-encoded canonical binary).
- C ABI is what WASM, JNI and Python bind to; Swift uses C++ interop directly against the C++ API but goldens run through both.
- No exceptions across the ABI: `Result<T>` with a stable `ErrorCode` internally, reason/error strings externally. Built with `-fno-exceptions -fno-rtti` for WASM.
- Alternative considered: Rust (v0.1). Rejected: desktop would need a second systems language and FFI for its main dependency.

### D2. Numerics
- `Fixed<Tag, Decimals>` int64 types with engine-wide scales (execution-policy v1): `Price` 1e-8, `Qty` 1e-8, `Money` 1e-8 credits, `Rate` 1e-10 (funding/fees/margin rates), `Vol` 1e-8. Fixed scales keep types compile-time checked; scenarios express granularity through tick/lot sizes that must be multiples of these scales. Headroom: int64 at 1e-8 holds up to ~9.2e10 units; intermediate products use `__int128`.
- Decimal strings (`"123.45"`) are the only text form: strict parser (no exponent, no excess fractional digits — never silent rounding).
- Multiplication/division use `__int128` intermediates with explicit rounding mode per call site (`floor`, `ceil`, `half_even`, `against_player`). Rounding modes are part of the execution-policy version.
- Overflow checks on every arithmetic op in debug and on boundary ops (notional, P&L) in release.

### D3. Floating point only inside pricing kernels
- Black-76, Greeks and IV use `double` with: `-ffp-contract=off`, no `-ffast-math`, no `long double`, no `std::exp/log/erf`. Engine kernels `det::exp`, `det::log`, `det::norm_cdf` implemented with argument reduction + fixed polynomial coefficients using only `+ − × ÷ sqrt` (IEEE-754 correctly rounded on all targets, including WASM).
- Results quantized to `Money`/`Vol` fixed-point immediately; state never stores doubles.
- x87 is excluded (x86-64 SSE2 only). Verified by the golden matrix, not by reasoning.

### D4. PRNG
- PCG32 (XSH-RR) with explicit stream ids per purpose (`Market` 1, `Events` 2, `Slippage` 3, `Sandbox` 4; never renumbered). Normal variates via engine Box-Muller using `det::log`/`det::sqrt`/`det::cos` kernels. Never `std::*_distribution` (enforced by `tools/check_engine_bans.py`).

### D5. Data model and step loop
- `Scenario` (immutable, validated), `RunState` (positions, orders, balances, rng, step, full event log), `Command`, `Event`.
- `start_run(sc, seed)`, `apply_command(sc, st, cmd) -> CommandResult` (at the current decision point, before advancing) and `advance(sc, st)` (one bar) implement the fixed step sequence from the spec. `advance` runs `open_phase` (gap liquidation, gap-triggered stops/limits, market orders), `option_open_phase`, `intrabar_phase` (adverse exits, favorable exits, entries, post-entry adverse sweep) and `close_phase` (funding, close liquidation, option expiry and margin call, trailing ratchet, metrics, finish/bankruptcy), each split into small functions to keep per-function complexity ≤ 15.
- News items are scenario data published at their release step; their market reaction is baked into the generated bars, so there is no engine-side event release phase.
- Event-sequence numbers are global per run; events are appended to `RunState::events`.

### D6. Liquidation & margin formulas (execution-policy v1)
- Isolated long liquidation price: `L = (q·m·E − M) / (q·m·(1 − mmr))`; short: `L = (q·m·E + M) / (q·m·(1 + mmr))` where `q` quantity, `m` multiplier, `E` entry, `M` isolated margin (after funding), `mmr` maintenance rate. Rounded toward the side that liquidates earlier (conservative). From policy v16, `mmr` is the rate of the contract's margin tier for the position's notional at its average entry (D6j).
- Liquidation forfeits full isolated margin (simplified vs. real exchanges that return residual; confirmed by product 2026-11-02). Bankruptcy check after each step: no positions/orders and available < IM + fees of min quantity at mission cap → `account_bankrupt`, run ends (game over).
- Option settlement target: Deribit-style TWAP over a declared window (default 30 min); mean of closes / expiry close fallback flagged approximate. Scenarios built for options chapters should include 1-minute sub-bars around expiries so settlement is exact (from policy v17, D6k; D6c describes v3).
- Short-option margin (default, scenario-overridable): IM = `max(0.15·F − OTM, 0.10·F)·m·q + ask·m·q`; MM = `0.075·F·m·q + mark·m·q`.

### D6b. Brackets, OCO and trailing (execution-policy v2)
- An entry may carry `attach_stop`/`attach_tp`. Each fill that grows exposure creates or grows reduce-only children (stop-market, take-profit) for exactly the increased quantity, sharing an OCO group = parent id. A fill on one child reduces its siblings by the same quantity; flat position cancels all reduce-only orders.
- Children can be created mid-bar, so `RunState::orders` is a `std::deque` (stable references) and matching iterates by index.
- An entry filled intrabar gets its children immediately; the post-entry adverse sweep may hit the child stop, but a same-bar take-profit is never credited.
- Trailing stop-market: trigger initialized from the decision-step close ± distance, ratcheted at each close (never loosened), effective from the next bar. Percentage trails were added in policy v16 (D6j).
- Policy v2 changed only the state serialization (new order fields); v1 event streams are unchanged.

### D6c. Options (execution-policy v3)
- Pricing: Black-76, zero rate, forward = perp close (display) or next open (execution). T from remaining steps × `minutes_per_step`. IV = base × term(T) + skew·ln(K/F) + smile·ln(K/F)², floor 5%. Base = scenario `iv_base[t]` (published at the close of t; the generator derives it from its volatility state + premium + per-segment event multiplier) or, when absent, annualized realized vol of the last 48 closes ≤ t (flag `ivFromRealized`).
- Quotes: mid quantized half-even to the premium tick; half-spread = max(spread × mid, 1 tick); bid floored (may be 0 → no bid), ask ceiled (≥ 1 tick). Greeks quantized (delta/gamma Rate, theta per step and vega per vol point in Price).
- Execution: option orders (market/limit) execute only at the next bar's open against a quote with F = open and IV published at the previous close — never intrabar, because the premium path inside a bar is unobservable. No capacity limit for options in v3 (documented approximation).
- Fees: `fee_rate` × underlying notional, capped at 12.5% of premium notional (venue-style).
- Margin: buyers pay premium (no margin). Writers: IM = max(im_base·F − OTM, im_floor·F) + ask; MM = mm_base·F + mid, per unit. Account option equity = wallet − isolated perp margin + longs at bid − shorts at ask. Below total MM after a step → `margin_call` event, buy back the short with the largest MM at the ask until satisfied; any shortfall is absorbed by the simulated insurance fund (wallet never negative).
- Settlement at the expiry close: TWAP of the last `settlement_bars` closes; with 1 bar it is the close and flagged approximate. Policy v17 replaces the bar count with a window in market time and sub-bars (D6k).
- Reconciliation: wallet = initial + perp realized − fees + funding + option_cash (premiums and settlements).
- Policy v3 adds the instrument (series) field to order/event serialization.

### D6d. Plans, calibration answers and scoring (execution-policy v4)
- `RecordPlan` stores the structured plan (side, invalidation, target, confidence, planned risk, skipped, option, has-lose-scenario) at the decision step; free text never reaches the engine (spec: no subjective grading).
- `AnswerQuestion` is accepted only when a question is due: every 15 steps from the first decision step, while the resolving bar (t+5) exists, once per step. Threshold = close at t; skipped answers are kept but not scored.
- `engine/scoring` (version 2; v2 changed only the calibration formula) derives entries from a position walk over perp fills and per-series option fills, protection from reduce-only stops placed in [t-1, t+2] (bracket children included), and computes risk/plan/calibration with renormalization, findings, next lesson and flat-to-flat trades (perpetual, and per option series closed by a fill or settled at expiry) with R = net / planned risk of the latest non-skipped plan of the same kind (perp or option). Integer arithmetic only, so client and server agree exactly.

### D6e. Generator v2 (execution-policy v5)
- Missions' bars come from the seeded market generator (`generator.hpp`, stream `Market`), which also emits the funding series and the `iv_base` series. Generator v2 changed the generated bars, so the policy version was bumped to 5; execution rules are unchanged from v4.

### D6f. Fill event order (execution-policy v6)
- `apply_fill` cancels orphaned reduce-only orders only after emitting the fill, and never the order being filled (it used to log the closing order as cancelled and then filled). The event log changes for every closed position, so the policy version was bumped to 6.

### D6g. Closing through capacity and m05 timing (execution-policy v7)
- A reduce-only market order (including "close position") whose remainder was cut by bar capacity stays `partially_filled` and keeps executing at the next opens until filled, the position is flat (orphan cancel) or the player cancels it. Other market orders stay IOC. Before, a large close could silently leave part of the position open.
- Bracket legs attached by a fill at the open go through the open-gap check too (a second pass after market orders): a stop computed from the previous close that the open already crossed used to fill at its trigger, above the bar's high for a long (found by a randomized playtest, m05 seed 9).
- Mission m05's jump moved from bars 120-122 to 100-102 (news at 99), before the first expiry (108), so options written at the start are still open when it hits; with the v8 implied vol, writing the at-the-money put of the first expiry gets a margin call in 7/40 seeds at 200 contracts, 28/40 at 300 and 37/40 at 400 (100: none). Both change replays, so the policy version was bumped to 7.

### D6h. Plausible implied vol (execution-policy v8)
- Generator `iv_base` priced the last bar's variance times every multiplier, so m05's jump published IVs above 2000% and margin-call buy-backs paid several times intrinsic value; the term factor `sqrt(T_ref/T)` also grew to 4.9x in an hourly option's last bar. v8 smooths the per-bar variance behind `iv_base` (factor 0.055, ~12-bar half-life), caps `iv_base` at 250%, and floors `T` at 7 days in the term factor. Measured over 30 seeds: calm chain IV 63-72%, peaks 156% (m04) and 290% (m05).

### D6i. Oversized exit remainder (execution-policy v14)
- A reduce-only exit larger than the position (a bracket leg left at its size after a partial close) used to close the position and stay `partially_filled` for one more bar, since the orphan cancel skips the order being filled; the next bar's `execute` then cancelled it. `execute` now cancels its remainder (`position_closed`) right after its own fill update when the position is flat. Events move one bar earlier in such runs, so the policy version was bumped to 14; every frozen event digest stayed the same and only the state digests (which include the policy number) changed.

### D6j. Capacity priority, percentage trails, margin tiers (execution-policy v16)
- **Capacity priority.** The step's phases keep the bar's chronology (open: gap liquidation, gap-reached stops and limits, market orders, then bracket legs attached at the open; intrabar: adverse exits, favorable exits, entries); that order is the conservative intrabar policy, not a priority choice. Within a phase, orders that compete for the bar's capacity are now served by price, then sequence (`priority_pass` in `engine/src/advance.cpp`), where before they were served in placement order: the level the market reaches first — at the open the signed distance along the gap from the previous close (a level the gap passed earlier ranks first, so a buy limit at 98 beats one at 95 when the price falls from 100 to 90), intrabar the distance from the open — then the command sequence (bracket legs carry their entry's), then the order id. Market orders and triggered stops' remainders at the open have no price to rank and are served by sequence. Eligibility is re-read after every execution, so a bracket leg attached by a fill joins the same pass.
- **Percentage trails.** `Command.trail_rate` / `Order.trail_rate` (Rate, appended to the order serialization; checkpoint format 4): a trailing stop gives exactly one of a tick-aligned distance or a rate in (0, 1), else `invalid_tick`. At placement and at every close the distance is `ceil(close × rate)` (1e-8) and the trigger is rounded outward to the tick (`detail::trail_trigger`, shared with fixed trails). C ABI `tl_place_trailing_rate(run, client_id, side, qty, reduce_only, rate)`, Python `Run.place_trailing_rate`, replay field `"trailRate"`; the state lists `trailRate` per order.
- **Margin tiers.** `ContractSpec.margin_tiers` (`MarginTier{notional_floor, maintenance_margin, max_leverage}`) above the base tier (`maintenance_margin`, `max_leverage`). The tier is chosen by the position's notional at its average entry (ceil), not at the mark, so the liquidation price stays the closed form of D6 and is recomputed exactly when the spec says (fill, margin change, funding). An order whose resulting position (existing notional at entry plus the increase at its reference price; at fill, at the fill price) sits in a tier whose cap is below the run leverage is rejected with `leverage_above_tier` (reason 33), and a resting order cancelled with it at fill; `SetLeverage` above the open position's tier cap is rejected the same way. The debrief's safe leverage goes through `liquidation_price`, so it uses the tier too. Built-in missions use the default contract's tiers: 0.5% (base, 50×) below 50,000 notional, 1% (20×) from 50,000, 2.5% (10×) from 250,000, 5% (5×) from 1,000,000; with 10,000 credits and mission caps of 2–20× no golden or learnability run reaches a higher tier. Packs keep their single `marginModel.maintenanceMargin` (manifest v1 has no tiers). The contract JSON lists `marginTiers` (base first, floor 0) so clients estimate liquidation with the same tier.
- The policy number in the state digest and the appended `trail_rate` field changed every frozen state digest; every frozen event digest stayed the same (no golden run has competing orders, a percentage trail or a position above 50,000 notional).

### D6k. Mark price, settlement window, continuity bars (execution-policy v17)
- **Mark price.** `Scenario.mark` holds one mark bar per traded bar (validated like a bar, same length); empty means the scenario marks from the last price (`mark_from_last_price`, the contract JSON's `markFromLastPrice`). `mark_bar(sc, i)` is the mark bar or the traded bar. The mark drives the open-gap liquidation (mark open; the liquidation closes at that open), the intrabar liquidation test (mark low for a long, high for a short), the close liquidation, funding (`quantity × multiplier × mark close × rate`; the funding event's price is the mark close), the account view's `mark` (unrealized P&L, equity, notional, the liquidation-distance metric) and the debrief's open-trade mark. Fills, stops, limits and capacity keep the traded bar: a wick on the last price alone triggers a stop but not a liquidation. Stop-versus-liquidation ordering compares the two levels as before. Option pricing and option margin keep the traded close as the forward (options are written on the traded perp price). Margin checks at placement already use the entry notional, so they need no mark. Every built-in mission and every pack (manifest v1 has no mark file) keeps the last price, so their runs execute exactly as under v16.
- **Settlement window.** `OptionSpec.settlement_minutes` (default 30) replaces `settlement_bars` (which no scenario set above 1). The window ends at the expiry close, i.e. `(expiry + 1) × minutes_per_step` minutes after the open of bar 0. `settlement_price` takes the TWAP of the last `window / m` closes of `Scenario.sub_bars` for the expiry bar (`SubBars{bar, minutes m, closes}`, the last close equal to the bar's close) when `m` divides the window and they cover it: exact, not flagged. Otherwise it averages the closes of the `ceil(window / minutes_per_step)` bars covering the window, flagged approximate unless those bars tile it exactly (window a multiple of the bar). An option order executes at the next open, so it is rejected with `series_settling` (reason 34) when that open (`(step + 1) × minutes_per_step`) is at or after the window start, and a resting option order is cancelled with it instead of executing at an open inside the window. Steps at or after the expiry keep `series_not_listed`. With hourly bars and the default 30 minutes the window starts inside the expiry bar, after its open, so built-in missions refuse and settle exactly as before; the chain JSON adds `settling` per quote and `settlementMinutes`, and the ticket explains a settling series instead of letting the engine refuse it.
- **Continuity bars.** `Bar.continuity` marks a bar the market did not trade: it must repeat the previous close (open = high = low = close) with zero volume, and bar 0 cannot be one (`InvalidContinuity`). It has zero capacity, so the open, option-open and intrabar phases do not run on it: no order executes or triggers, and working orders (market orders included) wait for the next trading bar's open, where they execute as usual. The close phase runs (funding at a boundary, close liquidation against the carried close, option expiry, trailing ratchet, metrics). `MissionRules.gap_policy`: `Skip` (default) computes indicators and candle patterns over the trading bars only and maps the values back, so a continuity bar has no value and SMA(n) is the mean of the last n traded closes; VWAP keeps sessions on real bar numbers and leaves continuity bars out. `CarryForward` feeds the continuity bars as they are (flat at the previous close, zero volume). No pattern completes at a continuity bar under either policy. The state JSON's bar tuple gains a seventh element (`continuity`) and the contract `gapPolicy`.
- **Where continuity bars come from.** CSV imports may fill each gap with continuity bars (`ImportRules.fill_gaps`, C ABI metadata `"gapFill": "none" | "skip" | "carryForward"`, default none = join the bars, as before): no volume and no funding on them, at most 20,000 bars in total (`too_many_bars`). The pack records `data.gapPolicy` and `bars.bin` then has a sixth int64 column (0 or 1); without `gapPolicy` the reader requires the five columns of before, so existing packs are byte-identical. This is the scenario-packs requirement that a gap inside the window is represented as declared continuity bars with zero capacity when the mission opts in.
- The policy number in the state digest changed every frozen state digest; every frozen event digest stayed the same (no built-in mission or golden pack has a mark series, sub-bars, a settlement window starting before an open, or a continuity bar).

### D7. Digest and checkpoints
- Canonical little-endian binary serialization of `RunState`; SHA-256 (vendored, constant-time not required). State digest covers the policy version, seed, step, status, leverage, balances, position, orders, option positions, plans, answers, metrics and RNG state; the events digest covers the full event log.
- Checkpoint = header (magic, checkpoint format 1, execution-policy version, scenario id) + serialized state. Loading fails with `IncompatiblePolicy`, `ScenarioMismatch`, `TruncatedInput` or `NonCanonicalEncoding`. The engine semver is not stored (reported by `tl_version`).

### D8. Golden vectors
- Goldens are SHA-256 digests frozen inside the doctest suite rather than a fixtures directory: kernel outputs (`test_det_math`), normal variates (`test_prng`), an option quote grid (OPT01, `test_options`) and scripted mission runs through the C ABI (`test_missions`, state + events digests). `bindings/python/tests` repeats a scripted run and checks the same digests. Update procedure: `engine/README.md`.
- CI runs them on: linux-x86_64 (clang 18), macos-arm64 (AppleClang), debug and release, wasm (node), python (ctypes). Swift added in `add-native-clients`.
- Property-style tests are seeded randomized loops (engine `Pcg32`, stream `Sandbox`) in doctest, not RapidCheck: reconciliation and non-negative balances (SIM08, with and without options), checkpoint resume. No-lookahead is checked by mutating future bars and comparing digests (SIM01, indicators, patterns, OPT04).

### D9. Bindings in this change
- WASM: Emscripten target `tradelab_wasm` (`-sMODULARIZE -sEXPORT_ES6 -sSINGLE_FILE`, exports the `tl_*` functions), built by `apps/web/scripts/build-engine.sh` into `apps/web/src/lib/engine/wasm/tradelab.mjs` and used from a Web Worker. TypeScript types are generated (see D10). `apps/web/scripts/check-wasm-size.mjs` fails the web CI job when the gzipped module reaches 400 KB.
- Python: pure-Python package `tradelab_engine` (`bindings/python/`) using ctypes over the C ABI in the shared library `libtradelab` (CMake target `tradelab_capi`), located via `TRADELAB_LIB`, the package directory or the engine build tree. Consumed by `services/api` (its image builds the library) for server re-simulation. ctypes was chosen over nanobind: the C ABI already exists for WASM, so no compiled extension or per-platform wheel is needed.

### D10. Interface definition (IDL)
- One IDL, `engine/idl/tradelab.idl`, declares the enumerations shared by state, commands, events and the debrief (numeric value + JSON name) and every JSON shape the C ABI returns (state, debrief, reveal, command results and payloads, CSV/pack results, checkpoints, errors). A small line-based syntax (enum / struct / union / tuple, `///` docs) rather than YAML: the generator (`engine/idl/gen.py`) needs only the Python standard library, so CI and contributors need no extra packages.
- Generated, never edited by hand: `engine/include/tradelab/idl_types.hpp` (C++ `enum class`es with their numeric values, which are part of the recorded-run format, and `json_name()` used by the C ABI writers), `engine/tests/idl_schema.hpp` (the shapes as JSON) and `apps/web/src/lib/engine/types.ts`. `gen.py --check` runs in the engine lint job and the web job and fails on a stale file.
- The engine's internal structs (`RunState`, `Command`, `Scenario`) stay hand-written: they hold fixed-point types and define the checkpoint encoding, which the IDL does not describe. What ties them to the IDL is `tests/test_idl_conformance.cpp`: it plays every mission (every command kind, options where listed), a CSV import, a pack run and the error paths through the C ABI and checks each output against the schema: exact keys, value types, declared enum names and decimal strings. Values outside the IDL (a hand-written TS constant such as `DEFAULT_RUN_OPTIONS`) live next to the generated file (`defaults.ts`).
- Generating the shapes surfaced two drifts the hand-written types had: a pack debrief also carries `marketMode` and `packDigest`, and `tl_csv_validate` with unusable metadata returns only `{ok, metaError}` (now `CsvMetaError`, part of `CsvValidation`), not a report.

## Risks / Trade-offs

- **Kernel accuracy vs. determinism** → kernels target ~1e-12 relative error; premiums are quantized to tick so any residual difference would show up as a golden failure, not a silent drift.
- **Simplified liquidation (full margin forfeit)** → may overstate losses vs. some venues; disclosed in UI and debrief.
- **OHLC conservatism penalizes favorable exits** → flagged `ambiguousIntrabar`; sub-bar data replaces it when licensed.
- **WASM bundle size** → budget < 400 KB gzipped, checked in the web CI job (single-file module: ~183 KB gzipped with the full mission catalog).
